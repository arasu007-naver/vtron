STAGE 0

PRODUCT CONTEXT — 판매 상품 먼저 정하기

v2에서 새로 생긴 단계입니다. 타깃을 찾기 전에 상품 의복을 정해 STAGE 1로 넘깁니다.

이 프롬프트 뒤에 PRODUCT CONTEXT 블록이 있는가?
NO이 단계를 건너뛰고, product_match를 내지 않음
YES상품명 · 카테고리로 판매 중인 의복을 찾는다 ↓
보이는 의복 중 상품에 맞는 것이 몇 벌인가?
정확히 1벌그 의복만 prominence: "dominant" + product_match: true, 나머지는 secondary / minor
0벌 · 2벌 이상아무에게도 붙이지 않고 이미지로 prominence 결정
경계

PRODUCT CONTEXT는 대표 의복 선택에만 쓰고, 관찰값 · 카테고리 · 적격성 · 색상 · 연출 유형을 바꾸지 않습니다.

v2 #14STAGE 0 추가 PRODUCT CONTEXT 지시가 user prompt에만 있어 STAGE 1(타깃 식별)보다 늦게 읽히던 문제. system prompt에 STAGE 0을 두어 타깃 식별 전에 상품 의복을 정한다. user 쪽 PRODUCT CONTEXT 블록은 그대로 두었다(데이터 + 같은 지시).
STAGE 1

타깃 식별

이미지 안의 의복을 하나씩 찾아 identity · readability · prominence를 정합니다.

target_id

배열 순서대로 target_1, target_2, …

의복 간 관계(cross_target_visual_relations)도 이 id로 가리킵니다. 엔진이 붙이는 id(target_N)와 같은 규칙입니다.

PROMINENCE · PRODUCT MATCH

STAGE 2 · A

카테고리 합성

특징 하나가 카테고리를 정하지 않습니다. 몸판 원단 · 구성 · 거동 · 트림 · 착용 역할을 함께 봅니다.

기존 규칙 (변경 없음)
  • OUTERWEAR HEM-FIRST — 아우터는 밑단 위치 → 신체 구간 → 길이 도메인 → 구성 → 카테고리 순
  • KNIT-BODY 니트 몸판이면 지퍼 가디건도 Sweater · SWEAT-BODY 스웨트 몸판이면 후드 집업도 Sweatshirt
  • OUTERWEAR-COLUMN 무거운 롱 아우터는 민소매라도 Coat · SHIRT vs JACKET 겉에 걸치는 오버셔츠는 Jacket
자기 토큰이 없는 의복 — 구조로 매핑
의복카테고리
패딩 · 퀼팅 · 다운 조끼, 겉에 입은 웨이스트코트Jacket + sleeve = Sleeveless (무릎 아래까지 오는 롱 아우터면 Coat)
니트 조끼Sweater + sleeve = Sleeveless
탱크톱 · 캐미솔 · 튜브톱 · 크롭톱 · 스포츠 브라 · 저지 바디수트T-Shirt (소매가 없으면 Sleeveless). 플래킷 · 셔츠 칼라가 있는 우븐 상의는 Shirt
블라우스Shirt (러플 넥은 collar = Ruffle)
반바지 · 버뮤다 · 바이크 쇼츠Trouser (length = Short / Knee Length)

Padding — 충전 · 퀼팅이 보일 때 Padding과 겉감 소재(보통 Synthetic)를 각각 material 값으로 냅니다. 보이지 않는 안감 충전재는 내지 않습니다.

STAGE 2 · B

적용성 — 어떤 키를 낼 것인가

키를 생략하는 것은 "해당 없음"이라는 계약입니다. "안 보임"은 NOT_VISIBLE, "판단 불가"는 UNKNOWN입니다.

NOT-APPLICABLE

카테고리별 금지 키 → 생략

ABSENT · None · null로도 내면 안 됩니다.

REQUIRED KEYS

카테고리별 필수 키 → 반드시 존재

T-Shirt · Shirt 19 · Sweater · Sweatshirt 20 · Jacket · Coat · Jumpsuit 21 · Trouser · Skirt 14 · Dress 23

CONDITIONAL

부모 관찰이 켜면 반드시 따라 나옴

sleeve ≠ Sleeveless → cuff_type · sleeve_volume / cuff_type ≠ None → cuff_scale / collar ≠ None → collar_scale

REQUIRED KEYS의 두 가지 예외 (v2부터 명시)
  • Jacket / Coat의 closure_type — front_opening_extent = None(앞트임 없는 아노락 등)이면 생략. Partial / Full이면 필수.
  • waist_definition — Coat · Dress · Jumpsuit는 두 게이트를 늘 통과하므로 항상 필수. Jacket은 Hip Length 이상일 때만 필수, Cropped / Waist Length면 생략.
v2 #2앞트임 없는 아우터의 closure_type Jacket / Coat에서 필수인데 값 도메인에 None이 없어 정상 답이 없던 문제. 엔진 검증기는 이미 이 경우를 해당 없음으로 보므로 "생략"으로 맞췄다. closure_type 블록의 "Jacket / Coat에 낸다" 문장도 함께 고쳤다.
v2 #3waist_definition 필수 여부 엔진은 게이트를 통과하면 키를 요구하는데(APPLICABLE_KEY_MISSING) 프롬프트의 필수 목록에는 없던 불일치. 목록의 개수는 엔진 기준 그대로 두고 예외로 적었다.
보류 #4끈 없는 · 민소매 드레스의 shoulder_drop / shoulder_structure 어깨선이 없어 None이 "해당 없음"으로 오염되는 문제. 그러나 Dress에서 두 키는 엔진의 필수 키라 생략하면 검증기가 거부한다 — 엔진 규칙을 함께 바꿔야 한다.
STAGE 2 · C

파라미터 읽기

파라미터마다 정해진 canonical 값 하나(MULTI는 값 목록)를 증거와 함께 냅니다.

관찰 원칙

파라미터끼리 서로를 근거로 삼지 않는다

단계 순서(먼저 훑고, 나중에 정한다)는 그대로 따릅니다.

v2 #11"no reasoning chains" 문구 "WORK IN EXPLICIT STAGES" · "sweep first, decide second"와 충돌하던 문구를 원래 뜻대로 "파라미터끼리 근거 삼지 말 것"으로 바꿨다.
fit

의복 전체를 훑고 한 번 답한다

어깨 → 가슴 · 몸통 → 허리 · 밑단 순으로 여유를 본 뒤 답합니다. Dress · Jumpsuit는 상체 · 하체를 따로 훑어 byRegion.upper / byRegion.lower에 각각 답합니다.

v2 #8Dress / Jumpsuit fit REGIONS 규칙(영역별)과 fit 규칙("한 번만 답한다")이 충돌하던 것을 한 줄로 정리했다.
grammar (Jacket / Coat)

구성으로 가른다 — 스타일 인상 아님

  • Tailored 라펠 · 테일러드 칼라, 셋인 소매와 각진 어깨, 단추 앞판 (블레이저 · 체스터필드)
  • Utility 여러 Applied / Volumetric 포켓, 플랩 · 스톰 플랩 · 견장 · 드로코드 (필드 · 사파리 · 카고 · 파카 · 아노락)
  • Casual 그 밖의 부드러운 쉘 (블루종 · 봄버 · 데님 재킷 · 유틸리티 하드웨어 없는 패딩)
v2 #9grammar 정의 필수 키인데 Tailored / Casual / Utility를 가르는 기준이 없던 문제. trouser_distinction처럼 구성 근거로 정의하고, 증거에 본 구성을 적게 했다.
pocket

None / Present → 포켓마다 pocket.pockets[] 항목

각 항목이 location + construction(Inset / Applied) + projection(Flat / Projected / Volumetric)을 함께 가집니다. 최상위 pocket_construction · pocket_projection 키는 없습니다.

v2 #5폐기된 포켓 키 세 번 폐기했다고 하면서 [POCKET] 첫 문단과 값 도메인 목록에 최상위 파라미터처럼 남아 있던 것을 pockets[].construction / .projection으로 옮겼다.
STAGE 2 · D

보조 필드의 자리

보조 필드는 파라미터가 아니고 자기 키가 되지 않습니다. 정해진 자리에만 씁니다.

필드자리
product_context타깃의 category 객체 안 (observations 아님)
locations[] · coverage · finish_realization · treated_surface_realization그 값을 설명하는 MULTI values[] 항목 안 — 예 {"value":"Glossy","finish_realization":"Enhanced"}. coverage는 [COVERAGE] 블록이 정한 값에만 (graphic · pattern · exposure_opening에는 쓰지 않음)
visual_dominance · motif_complexitypattern 관찰 객체 자체, value 옆 (pattern이 OBSERVED일 때만)
pockets[]pocket 관찰 안
v2 #6product_context · 보조 필드 위치 값 정의만 있고 JSON 어디에 넣는지 없던 문제. 엔진 검증기 · 컨트롤러가 읽는 자리에 맞춰 출력 템플릿과 위 표를 넣었다.
v3coverage 문장 수정 v2의 이 안내에 "graphic · pocket의 coverage는 관찰 객체에"라고 적었는데, 기존 [COVERAGE] 규칙("NOT on graphic", coverage를 받는 값 목록)과 충돌했다. 검증기는 허용하지만 프롬프트 안에서 서로 다른 말을 하지 않도록 [COVERAGE] 규칙을 따르게 고쳤다.
