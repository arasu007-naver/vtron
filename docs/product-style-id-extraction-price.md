# 상품 Style ID 추출 — Claude API 사용료

`/style-ex` 의 **상품 Style ID 추출** 한 건에 드는 Claude API 비용 산정과, 이를 줄이기 위한 관찰 프롬프트 캐싱.

- 산정 대상: `product_style.id = d57749d3-5df3-427d-84b4-9160376bd6e4`
  (디올 30 몽테인 바 자켓, `model_id = 30269066618`, 결과 `ICSM`, 2026-10-11)
- 가격: Anthropic 1st-party API 정가 (2026-10 기준, 1M 토큰당)
- 환율 가정: $1 = 1,400원

## 1. 한 건에 일어나는 Claude 호출

| 단계 | 모델 | 입력 | 출력 |
|---|---|---|---|
| ① 관찰 | `claude-opus-4-8` (thinking 없음) | 상품 사진 + 관찰 프롬프트 | 의복별 37개 파라미터 · DM 디테일 · 색상 · 연출 유형 JSON |
| ③ 판정 | `claude-opus-5-5` (effort `high`, adaptive thinking) | 판정 프롬프트 + 대표 의복 관찰값 JSON | 4개 축 글자 · 근거 JSON (+ 사고 토큰) |

엔진 스코어링(②)은 서버 안에서 도는 JS 라 API 비용이 없다. 부위 크롭은 별도 버튼이며 이 산정에 포함하지 않았다.

## 2. 산정 결과 (캐싱 적용 전)

| 호출 | 단가 (입력 / 출력) | 입력 토큰 | 출력 토큰 | 비용 |
|---|---|---|---|---|
| ① 관찰 | $5 / $25 | **68,068** (실측) | 약 2,600 ~ 4,000 (추정) | **$0.41 ~ $0.44** |
| ③ 판정 | $4 / $20 | **14,063** (실측) | 답 약 1,200 + 사고 토큰 (미상) | **$0.12 ~ $0.24** |
| **합계** | | 약 82,000 | | **약 $0.53 ~ $0.68 (약 750 ~ 950원)** |

### 산정 방법

- **입력 토큰 — 실측.** 무료인 토큰 계산 API(`messages.countTokens`)에 실제 요청과 같은 내용(같은 상품 사진 + 같은 프롬프트,
  판정은 같은 관찰값 JSON)을 넣어 셌다.
- **관찰 출력 — 추정.** 모델이 낸 원문은 저장되지 않는다. DB 의 정리된 관찰 결과를 JSON 으로 다시 만들어 센 값이라 오차가 있다.
- **판정 출력 — 추정.** 보이는 답(JSON)은 약 1,200 토큰. effort `high` 의 사고 토큰도 출력 단가로 청구되지만 양은 응답의
  `usage` 에만 나와 알 수 없다 — 2,000 ~ 8,000 토큰으로 가정했다.
- 앱은 응답의 `usage` 를 저장하지 않는다. 정확한 금액은 Anthropic Console 의 사용량 화면에서 확인해야 한다.

### 비용 구조

- **관찰 프롬프트 입력이 전체의 약 60%** ($0.34). 관찰 프롬프트는 약 68,000 토큰이고, 상품마다 똑같은 내용이 매번 전송된다.
- 상품 사진 자체는 작다 — 이번 원본(`products.image_url`)은 11KB JPEG 였다. 해상도가 낮으면 관찰 정확도가 떨어질 수 있다.

## 3. 관찰 프롬프트 캐싱

### 적용 내용 (`lib/style-ex/extract.ts` 의 `observe`)

- 관찰 요청의 내용 순서를 **[관찰 프롬프트, 이미지]** 로 바꾸고, 관찰 프롬프트 블록에 `cache_control: { type: "ephemeral" }` 를 붙였다.
  - 캐시는 요청 앞부분(prefix)이 바이트 단위로 같을 때만 맞는다. 이전에는 **[이미지, 프롬프트]** 순서라 상품마다 다른 이미지가
    앞에 있어 캐시가 걸릴 수 없었다.
- 캐시 유지 시간은 기본 5분(마지막 사용 시점부터 연장). 상품을 이어서 추출하면 계속 캐시를 읽는다.
- 관찰 프롬프트를 편집해 보낸 경우에도 같은 편집본이 반복되면 캐시가 걸린다.
- 서버 로그에 호출마다 `[style-ex] 관찰 usage` (입력 · 캐시 쓰기 · 캐시 읽기 · 출력 토큰)를 남긴다 — 캐시가 실제로 맞는지 확인용.

### 기대 효과 (① 관찰 입력, Opus 4.8)

| 경우 | 관찰 프롬프트 약 68,000 토큰의 단가 | 비용 |
|---|---|---|
| 캐싱 전 | 매번 정가 $5 | $0.34 |
| 첫 호출 (캐시 쓰기) | 1.25배 $6.25 | 약 $0.42 (+$0.08) |
| 5분 안의 다음 호출 (캐시 읽기) | 0.1배 $0.50 | **약 $0.03** |

상품을 연속으로 추출하면 두 번째부터 **한 건당 약 $0.30 절약** — 한 건 비용이 약 $0.53 ~ $0.68 에서 **약 $0.23 ~ $0.38** 로 준다.
5분 넘게 쉬었다가 다시 추출하면 그 첫 호출은 다시 캐시 쓰기($0.42)가 된다.

## 4. 의류 구분(상의 · 하의 · 원피스 등)을 미리 주면 비용이 줄어드는가

상품은 카탈로그에서 카테고리(`kind` · `path`, 예: `여성의류>아우터>재킷`)를 이미 알고 있다. 이를 관찰에 넘겨 프롬프트를
그 카테고리용으로 줄이면 얼마나 줄어드는지 토큰 계산 API 로 실측했다 (해당 없는 파라미터의 규칙 줄과, 다른 카테고리 전용
길이 · 실루엣 줄을 뺀 프롬프트 기준).

| 카테고리 | 해당 없는 파라미터 | 줄어드는 입력 토큰 | 관찰 입력 대비 | 캐싱 없을 때 절약 | 캐시 읽기일 때 절약 |
|---|---|---|---|---|---|
| Dress | 3 | 약 2,900 | 4% | $0.015 | $0.0015 |
| Jacket | 8 | 약 3,700 | 5% | $0.018 | $0.002 |
| T-Shirt | 8 | 약 6,500 | 10% | $0.032 | $0.003 |
| Trouser | 20 | 약 9,800 | 15% | $0.049 | $0.005 |
| Skirt | 20 | 약 11,900 | 18% | $0.060 | $0.006 |

(관찰 입력 전체 약 67,500 토큰 = Producer 프롬프트 61,400 + 색상 지시 5,900 + 연출 유형 200)

**결론: 줄기는 하지만 작다. 캐싱을 적용한 지금은 사실상 의미가 없다.**

- **입력** — 한 건당 $0.015 ~ $0.06 (캐싱 전 기준). 캐싱을 쓰면 이 부분은 이미 0.1배라 절약이 $0.002 ~ $0.006 로 준다.
  게다가 카테고리별 프롬프트가 생기면 캐시가 최대 10갈래로 나뉘어 각자 캐시 쓰기(1.25배)를 따로 치르므로, 추출이 띄엄띄엄이면
  오히려 비싸질 수 있다.
- **출력** — 거의 그대로. 모델은 이미 해당 없는 파라미터를 출력하지 않는다(키 생략 규칙).
- **판정** — 판정은 이미 대표 의복 하나만 본다. 카테고리를 알아도 규칙을 덜어낼 부분이 적다.
- **품질 위험** — 관찰 프롬프트는 엔진의 동결된 최종본이다. 잘라 쓰면 검증된 프롬프트와 달라진다.

**카테고리 정보가 실제로 도움이 되는 곳 — 출력과 대표 의복 선택**

- 착용 사진처럼 한 장에 옷이 여러 벌 보이면, 관찰은 보이는 옷을 **전부** 관찰한다(의복 1벌당 출력 약 2,600 ~ 4,000 토큰,
  $0.07 ~ $0.10). 상품 카테고리에 맞는 옷만 관찰하게 하면 추가 의복만큼 출력 비용과 시간이 준다. 단, 이는 "보이는 모든 옷을
  관찰" 하는 엔진 규칙을 바꾸는 일이다.
- 지금 대표 의복은 "가장 눈에 띄는(dominant) 옷"으로 고른다. 재킷 상품을 바지까지 입은 착용 사진으로 추출하면 바지가 대표가
  될 수 있다. 카테고리로 대표 의복을 고르면 비용은 같아도 **엉뚱한 옷의 Style ID 가 저장되는 것**을 막을 수 있다.

### 남은 개선 여지

- **판정 프롬프트 캐싱** — 약 12,000 토큰이 매번 같다. 같은 방식으로 앞에 두고 캐시하면 한 건당 약 $0.04 더 줄일 수 있다.
- **`usage` 저장** — `product_style` 에 관찰 · 판정 응답의 `usage` 를 저장하면 추정 없이 건별 정확한 비용을 낼 수 있다.
