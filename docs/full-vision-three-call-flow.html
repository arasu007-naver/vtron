착장 전체 비전 3회 추출 흐름

관찰 프롬프트 v1.2 "비전 호출 3+"(FULL_LOOK_OBSERVE_V1_2_THREE_CALL)로 착장 사진 한 장의 관찰 JSON을 만드는 흐름입니다. v1.1의 규칙 문장은 그대로 두고, 한 번에 하던 관찰을 ① 등록 → ② 외관 ∥ ③ 구조·관계의 비전 3회로 나눕니다. 세 결과는 코드가 v1.1 §8a 모양의 JSON 하나로 합치므로, 그 뒤의 정리 · 동결 추출 엔진 · 채점 엔진은 비전 1회와 같습니다. 따로 단추는 없습니다 — 관찰 프롬프트로 v1.2를 고르고 [추출]을 누르면 3회로 돕니다.

호출마다 맨 앞의 SCOPE OVERRIDE

규칙 문장은 세 호출이 함께 쓰므로 "적용되는 사실을 모두 내라" 같은 문장이 남아 있습니다. 각 프롬프트 맨 앞에서 "그 말은 이 호출의 출력 모양에 있는 사실과 키만을 뜻하고, 나머지는 다른 호출이 답한다"고 범위를 좁힙니다.

합치기

merge(①, ②, ③) → v1.1 §8a 객체 하나

관찰값은 바꾸지 않습니다. 키마다 주인 호출의 값만 받고, 남의 범위에서 온 값과 등록되지 않은 ref는 버리고 merge_log에 남깁니다.

§8a 키주인합칠 때
frame · objects①where 삭제
colour_areas · detail_systems②carrier / carrier_refs가 등록에 없으면 버림 (DROP_UNKNOWN_REF)
facts 외관 6②③이 외관 6을 내면 버림 (DROP_OUT_OF_SCOPE)
facts 그 밖③②가 구조 사실을 내면 버림 (DROP_OUT_OF_SCOPE)
front_state · upper③③이 없으면(②③ 생략) upper = governing null · 세 상태 NOT_VISIBLE
layer_relations · securing_relations · exposure_supplement③ref가 등록에 없으면 버림 (노출의 carrier UNKNOWN은 허용)

오프라인 확인: EX-04 표본 응답 12개를 세 호출의 출력처럼 나눈 뒤 합쳤을 때, 12개 모두 비전 1회와 같은 패킷(사실 풀 · 색 구성 · 디테일 시스템)과 같은 EI · TC · SR 방향이 나오고 merge_log는 비었습니다. 합치기에서 정보가 사라지지 않는다는 뜻이고, 3회 관찰이 더 정확한지는 실제 호출로 따로 재야 합니다.

점검

실제 호출로 확인할 것

프로토타입은 오프라인 합치기만 검증됐습니다. 유료 실호출(G53 승인 필요)로 아래를 재야 1회 방식과 비교할 수 있습니다.

확인 1정확도 · 안정성 EX-04 12장을 1회(v1.1)와 3회(v1.2)로 각각 3번씩 돌려, 판정을 가르는 사실(지배 상의 relation · shoulder · shape, fit, 색 standing)의 기준 일치율과 같은 이미지에서 방향이 매번 같은지 비교한다.
확인 2등록이 ②③에서 지켜지는가 where 설명만으로 ②③이 같은 물체를 가리키는지 — merge_log의 DROP_UNKNOWN_REF, 색이 없는 참여 물체(검증 오류 G1_NO_COLOUR_OPPORTUNITY)를 센다. 어긋나면 ①이 물체마다 대략적 위치 상자를 내게 하는 방안을 본다.
확인 3비용 · 시간 호출별 usage로 이미지 1장당 입력 · 캐시 · 출력 토큰과 소요 시간을 잰다. ③이 29,310자로 가장 크므로, 캐시 적중 후에도 무거우면 §5 · §6의 중복 문장을 줄인다.
